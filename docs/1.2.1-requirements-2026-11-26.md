# Synca 1.2.1 需求讨论记录

更新日期：2026-11-26。以下为用户确认的产品方向，不代表代码已实现或发布；具体工程方案及验收待补齐。

## 已确认方向

- 草稿本：每账号一页，全端自动保存和同步，随时续写；支持 Markdown 和图片，侧栏独立入口。离线保存、冲突保留、图片长期保存需要设计。
- 升级：Windows 本次支持下载后重启自动更新，包含现有便携包迁移评估；iOS 和 Mac 商店版检查后跳转商店更新。
- 桌面账号菜单：删除菜单顶部重复头像，保留账号信息；底部账号入口不在本次删除范围。
- 截图：Mac、Windows 一致体验；全局快捷键、鼠标悬停拾取窗口、点击锁定或拖框选区、矩形标注、确认复制到剪贴板、保存、取消。快捷键及工具栏细节待设计。

## 收藏：最终取舍

- 收藏为长期资料区域，不是待办。支持普通文字、账号资料、图片和文件，不做专门的密码管理。
- 待办进入收藏是快捷路径：从普通待办列表移出，不计入待办数字，不显示完成按钮，不因原完成状态变灰。
- 不提供移回待办/取消收藏的往返操作；删除是独立操作。也可在收藏中直接新增。
- 侧栏提供收藏入口；进入后侧栏选中收藏，点击外侧分类返回普通待办视图。
- 分类全局一套，只有一个管理入口；不建立收藏专用分类管理，不增加“在待办侧栏显示”开关，不建立分类适用范围。
- 接受收藏使用的分类也出现在全局侧栏，不通过数量自动隐藏。
- 收藏页提供分类筛选，当前讨论采用下拉；默认可查看全部。新建默认采用当前筛选分类，全部视图下采用系统默认分类；新增时显示实际归属。
- 全局搜索同时检索待办与收藏，结果明确标记收藏；收藏页不另做搜索。附件正文/OCR 不在当前承诺范围。
- 收藏不插入普通待办排序，不置顶、不设普通列表内收藏折叠区。
- 附件长期保留、不按普通待办附件期限清理，仍受容量限制；已过期附件不能凭收藏恢复。具体配额和套餐规则待定。
- 多端及 MCP 均需支持收藏及分类、搜索语义。

## 免费 / Pro 边界（已确认）

- 截图与升级提醒免费。
- 草稿本、收藏向免费用户开放。
- 图片和文件统一计入现有账号容量：免费 100 MB，Pro 1 GB；不为草稿、收藏各赠送一份容量。
- 普通文件上传和 MCP 继续沿用当前 Pro 权限。
- 长期保存不等于无限容量；既有附件转换到收藏不可重复计费。

## OSS 暂缓（已确认）

继续使用现有服务器云盘，不开通 OSS，不迁移久念媒体。原因是磁盘有余量，当前阶段新增费用与迁移复杂度超过即时收益。开发收藏与草稿时落实附件引用、权限、容量与清理保护；生产备份现状需独立核查，未声称已验证。

## 开发顺序和执行边界

1. 菜单精简与版本基线核查。
2. 收藏：服务端迁移、权限、配额、旧客户端兼容、清理保护，再接 Web/Electron、iOS 和 MCP。
3. 草稿本：本地恢复、同步版本冲突、Markdown 和图片，再接各端入口。
4. 升级：版本清单与商店跳转；Windows 安装与更新链路、旧便携版迁移。
5. 截图：先验证双平台窗口拾取与权限，再实现共同的选区、标注及剪贴板交互。

已授权进入开发。继续使用当前主目录，避免重新生成大量 worktree。开发授权不代表本轮已部署或发布；发布记录须区分本地验证、平台运行验证及生产验证。

## 实现默认值（工程建议，不冒充新增用户要求）

- 草稿首版沿用 Markdown 文本编辑及预览方向，不默认引入完整富文本文档系统；图片必须使用持久附件标识，不写入会过期的签名链接。
- 自动保存先持久化本机，再同步服务端；并发冲突保留双方副本，不静默用后写覆盖。
- 容量不足阻止新增附件，不影响已有资料读取、文本编辑、删除和释放容量。
- 截图仅在用户调用时获取屏幕，默认复制结果，不自动上传或保存到收藏。
- Windows 先验证安装包及签名条件，不自动购买签名证书或声称未签名包没有系统提示；重启更新前保存本地草稿。

## 2026-11-27 追加：Windows 双渠道分发（同版本、同 dev 分支）

本追加替代旧“仅本地、不发布”的执行边界中与 Windows 分发冲突的部分：用户授权完成技术选型、编码、GitHub Actions Windows 构建、Windows 回归、准备商店材料并推进正式上架；需本人登录、身份认证或接受法律协议时交还本人。保持每项需求完成后本地提交。任何发布必须基于对应平台真实验证和已认证发布者身份，不能用测试身份上架。

### KANO 初判

官网自动更新为期望型 O，版本越多价值越高；旧数据和登录保留为基本可靠性 M。商店安装信任对新用户偏 M、对现有用户偏 O。依据为用户反馈及明确需求，缺少转化行为数据，分类属初步假设。收益是减少手动替换和安装疑虑；主要成本是 Windows 迁移、更新失败恢复、商店身份认证和长期维护。建议本版做，优先复用已有 Squirrel.Windows，商店用 MSIX 和 Store 更新；用 1.2.0（89）真实程序的隔离资料迁移测试、篡改拒绝、Windows 构建和认证报告验证。

### 官网 Windows 版

- 保留官网 x64/arm64 ZIP 便携包。1.2.0（89）不具备更新器，第一次须启动新的安装包；不声称能凭空给旧程序添加自动更新。
- 复用已有 Electron autoUpdater / Squirrel.Windows，检查、提醒、下载、重启安装、失败后继续使用和重试均需覆盖。
- 显式保持旧程序用户目录与登录／本地草稿／离线缓存，不迁移到空白的新目录，不删除旧便携目录。
- 可信 HTTPS 固定来源、架构和版本约束、文件大小和 SHA-256 校验；安装版更新包同样先验证完整性，不能只验证首次 Setup.exe。
- 不购买第三方签名证书，不宣称官网未签名包因此获得 Store 的安装信任。

### Microsoft Store 版

- 独立 MSIX 打包目标，复用现有 Electron 界面及主进程。Store 管理安装和更新，禁用应用内下载安装路径和 Squirrel 生命周期处理。
- 通过微软免费签名机制分发商店包；不采用需要自购证书的 Store EXE/MSI 路线。
- 中国大陆账户注册、本人身份验证、应用名称与包身份、提交资料和审核纳入本版本。当前文档对商业用途要求 Company，需按实际注册规则核实，不能擅自替本人声明非商业用途。
- 包身份必须从 Partner Center 取得。允许明确标记的临时 CI 验证身份，禁止将它当正式商店身份发布。
- Mac mini 开发，Windows Runner 构建、功能和迁移回归、MSIX 验证、截图；真实桌面交互与系统限制需分开报告。
- 商店文案、关键词、截图、隐私政策、年龄分级和审核说明均需准备；截图必须来自实际 Windows UI，不能以 Mac 承载前端图冒充。
- 网站版与商店版不同时写同一个 Chromium profile；官网旧版本迁移与商店跨渠道登录不能混为一谈。商店首次登录通过既有账户恢复云端资料，不删除官网本机内容。

### 长期维护与发布门槛

版本号、架构、包身份、官网目录、Store 包和更新职责有唯一文档；CI 产物留 SHA-256、提交号和测试日志。官网发布先原子放入版本文件，最后切换清单；商店更新只经认证流程。验证未完成时保留原线上版本。Web、iOS、原生 Mac 和现有线上用户不受影响。
